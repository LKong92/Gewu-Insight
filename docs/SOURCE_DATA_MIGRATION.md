# 给合作者 Codex 的数据迁移指令（macOS）

## 给合作者看的说明

这份文件交给你的 Codex 执行即可。它负责退出软件、备份、保护本地代码改动、拉取更新、迁移数据库、配置启动入口和验证；你不需要手工备份或敲命令。通常只需要回答“数据库放在哪里”，以及批准操作系统或 Codex 要求的必要权限。遇到无法自动判断的代码冲突或多个正式数据库时，Codex 才会询问你的选择。

这是一次性的数据目录整理，不要求制作或下载 DMG。整理后，项目目录保存开发代码，独立的 `Gewu Database` 保存你的研究数据。以后更新代码继续使用同一个数据库。

把本文件作为附件交给对方 Codex，并发送：

> 请按照附件《给合作者 Codex 的数据迁移指令》执行我这台电脑上的 Gewu 更新和数据迁移。退出软件、备份、保护本地改动、拉取代码、迁移、配置启动与验证都由你完成；只询问数据库位置和其他必须由我决定的问题。保留可恢复的原数据，不提交或推送我的本地改动，不制作 DMG。请用中文沟通。

必须在更新前拿到此文件：可以直接转发附件，或提供已发布提交中本文件的网页链接。不要让合作者先 pull 才能获得备份指令。当前文件未提交时，只能转发文件；不要声称远端已经包含它。

---

## 以下由接收方 Codex 执行

### 任务范围与沟通

- 用户发送上述请求后，按本文件完成操作，不要把退出、备份、Git 操作、路径检查或验证交回用户。先读取当地的 `AGENTS.md` 和 `PROJECT_STATE.md`，遵守当地工具权限。
- 全程用中文沟通，阶段性说明进展。已经获得授权的步骤不反复询问；超出文件权限时通过工具申请必要权限，不要求用户自己搬文件。
- 只处理本机 Gewu 更新、数据分离及其所需启动配置。不得修改无关功能、提交、推送、创建产品分支、强推、打包 DMG或更改其他项目。
- 此流程针对 macOS。若本机为 Windows，读取该平台分支的实际路径和迁移机制，先说明差异；不要直接套用 Finder、plist 或 macOS App 操作。
- 以下 `REPO`、`SOURCE`、`DESTINATION`、`BACKUP`、`PYTHON` 均为你实际发现或确认的绝对路径，不是要求用户填写的模板。程序调用优先使用参数数组；使用 shell 时正确引用含空格的路径。

### 第一步：发现本机状态，确认目标位置

1. 确认真正的源码目录、Git 顶层、分支、upstream、远端 URL、HEAD 和工作区状态。不要假定目录名、用户名、远端名或分支，更不要套用开发者电脑上的绝对路径。
2. 检查 Gewu App、后台进程、服务端口、启动脚本及现有数据库定位配置。通过实际进程、配置和只读数据库信息确认当前正在使用的数据库；不要仅按最近修改时间猜测。若有多个可能的正式库且证据不足，询问用户选哪个，禁止自动合并。
3. 区分源码 App、已有独立 App 与命令行启动；记录后续需要恢复的正常入口。不要把独立 App 内的旧代码当成已经随源码 pull 更新。
4. 在尚无已确认位置时，只问一次：
   “建议把研究数据放在源码项目旁的 `<实际父目录>/Gewu Database`，是否使用这个位置，还是指定其他本地目录？”
   等待回答期间可以继续只读检查。不得把等待超时视为同意。如果用户已经明确给出位置，直接采用。
5. 检查目标不是源码的子目录或父目录、不是现有库，也不会覆盖已有文件。估算备份与完整复制所需空间；空间不足时提出明确选项，再询问备用位置。已经完成迁移且当前启动指向正确库时，跳过重复迁移，转为更新和验证。
6. 阅读当前实际迁移代码的边界：当前工具接收包含 `data/paper_monitor.sqlite` 的工作区。若对方用了自定义 SQLite 名称、独立 `GEWU_DATA_ROOT` 或其他布局，先给出适配方案；不得假装标准命令已覆盖该布局。

### 第二步：由你退出软件并完成备份

1. 先正常退出确定的 Gewu App，等待其服务停止。正在导入、保存或下载时等待结束；有未保存内容或退出对话框必须由用户选择时才询问。核实源 SQLite、WAL 和 SHM 没有仍在写入的进程；不要用 `killall Python`、强制杀进程或终止无关端口服务。
2. 选择源码及新数据库目录之外、不会被 Git 管理的带时间戳备份目录，权限仅当前用户可读写。正常情况下自动选择同级目录，并记录位置。备份中可能有 API 密钥和 MCP 令牌：不要打印内容、上传或加入 Git。
3. 在 pull 之前完整备份源码工作区，包括隐藏文件、未跟踪/忽略文件、原数据库及文件、报告、配置、日志、原 App 和本地开发改动。macOS 使用保留扩展属性、资源叉、符号链接及权限的复制方式，例如 `ditto --rsrc --extattr`，不要递归解引用链接，也不要把备份复制进自身。
4. 保存 Git 的 HEAD、分支/upstream、状态、暂存和未暂存的二进制补丁以及未跟踪文件清单；确保本地提交可恢复。普通仓库备份包含 `.git`，若 `.git` 是 worktree 指针文件，另行备份关联 Git 元数据或验证覆盖本地提交的 Git bundle；不得破坏其他 worktree。
5. 仅从本机库中实际使用的文件路径、符号链接及 Finder 替身发现项目外的链接原文件，逐一复制到备份并记录原路径映射。不要把全部 `source_path` 导入历史误当成当前文件，不要扫描无关个人目录。已缺失的目标记入基线；原先存在但无法备份的文件属于阻碍，先解决权限或空间问题。
6. 备份即将修改的机器配置和 App，例如数据库定位 plist、Gewu 的 MCP 启动配置；浏览器 Cookie、登录资料和其他 App 配置不重置、不迁移、不扩大访问。
7. 验证关键 SQLite 副本可读且完整，比较实际复制文件清单及 SHA-256，确认研究文件、扩展属性和替身没有在复制中丢失。记录备份验证结果。备份未通过，不进行 pull 或迁移。

### 第三步：保护本地改动，再拉取最新版

1. 备份后判断更新是否会影响本地改动。需要暂存时，保存一个具名 Git stash 并记录其对象 ID，可包含未跟踪文件，但不要使用包含所有忽略文件的 `--all`，避免移动研究数据。确认忽略数据仍在原处。未跟踪文件如包含实际数据，应先按数据处理，不能盲目 stash。
2. 对已确认的 upstream 执行 fetch，然后 `git pull --ff-only`。不得用 `reset --hard`、`clean -fd`、强制 checkout、擅自切分支或重写历史来“解决”失败。
3. 若有本地提交造成分歧，保留全部提交，说明具体分歧和安全选项后询问用户。若仅为可机械解决的本地补丁冲突，可依据备份处理；涉及功能取舍才询问。不要自动提交解决结果。
4. 用 `git stash apply --index <记录的对象ID>` 恢复需保留的本地开发改动并核对。先 apply，验收完成前不要删除 stash；无关 stash 不动。不要恢复此次更新已替换的旧 App 文件来覆盖新架构；旧构建和对它的本地修改必须留在备份，并明确记录其处理结果。
5. 记录拉取前后的提交号，重新读更新后的 `PROJECT_STATE.md`、迁移代码和启动代码。确认包含 `paper_monitor/database_migration.py` 和 `paper_monitor/workspace.py`；若远端尚未提供，停止迁移并说明缺少什么，不从别人的机器复制私有数据或继续假定功能存在。
6. 使用本机项目的虚拟环境，按 requirements 补足依赖；不改系统 Python。先运行迁移命令的 `--help`，再进入数据操作。

### 第四步：复制、校验，暂不删除旧库

在确认后台服务仍已停止后，从更新后的源码目录执行，参数使用本机绝对路径：

```text
<PYTHON> -m paper_monitor.database_migration <SOURCE> <DESTINATION>
```

- 这是一份由 Codex 代入参数执行的命令，不要求用户输入。它复制到不存在的新目录，重写受管理的路径和 Finder 替身，保留原目录。
- 阅读工具实际输出以及新目录 `backups/workspace-migration.json`。只有命令成功、`verified` 为 `true`、记录的 source/destination 正确且独立抽查通过，才允许切换启动位置。
- 对照基线核对记录数量、论文标识、文件分类、放置关系、默认文件、AI 分析和授权设置；路径变更必须符合预期。检查 SQLite 完整性与外键，抽查真实 PDF、Markdown、附件、Space 和 My Publications 的文件散列以及替身目标。
- 原先缺失的文件必须明确列为“迁移前已有”，不能宣称已修复，也不能把新增缺失混入该类别。不要为验收在正式库中制造论文、分析或导入记录。
- 原目录中未由工具搬走的历史备份、日志或开发文稿保留在备份中，不擅自删除。Paper Files 中的分析随对应文件迁移，不另行重复生成。
- 失败时保存部分目标和日志，不切换、不覆盖重跑、不删除源。修复原因后，使用另一个新目录重试；涉及更换用户选定最终位置时说明原因并确认。

### 第五步：由你配置日常启动，不能只完成文件复制

先识别实际启动方式，再做最小调整。**不得只在一个终端临时 export 后宣布完成，也不得把浏览器界面默默替代原生 App。**

1. 源码启动必须持久指定 `GEWU_WORKSPACE_ROOT=<DESTINATION>` 和 `GEWU_DATA_ROOT=<DESTINATION>/data`。配置放在本机私有且不被提交的位置；普通双击或原来的入口重启后仍应生效。
2. 启动前验证目标 SQLite 存在且身份正确。复用更新后的 `workspace.prepare_workspace(..., create=False, expected_identity=...)`，在修改 schema 前备份，保持进程锁；环境变量必须在导入 `config`/`cli` 前设置。数据库不存在或身份不符时停止，不得创建一个空库顶替。
3. **源码原生 App：**检查原生主程序和 Server helper。当前模板 helper 会按 App 所在位置寻找源码，并创建项目内 data/reports；`build_macos_app.sh` 本身并不替你改这些引用，原生路径选择器目前也仅用于独立 App。不要直接把新构建移到 Applications 后就认为能启动。必要时由你在本机制作最小启动适配，明确源码、虚拟环境、数据库、日志和认证文件路径，使原生进程与后台使用同一库；复用已有构建/签名流程，在临时位置验证后替换已备份的日常入口。不需要制作 DMG，不改研究业务逻辑。
4. **原来使用命令行/浏览器界面：**由你建立持久启动脚本，绑定正确解释器、源码和数据库，包含上述启动检查；不要让用户每次手工输入路径。先确保端口没有其他服务占用。
5. **已有独立 App：**源码 pull 不会更新其内置代码。仅在核实其版本支持目标 schema、路径和定位机制后才允许连接。否则报告具体阻碍并提出源码启动适配方案，不把安装包重建偷偷加入任务。
6. 若使用 MCP，备份后只修正已有 Gewu 项目的启动解释器/脚本、必要环境或服务地址；保留用户自己的令牌、权限及其他 MCP 配置。检查它连接的是当前正式服务，不得复制开发者的令牌。若客户端必须重新连接，由你通过可用工具操作；确需用户点击时说明唯一必要动作。
7. 后端健康检查必须核对实际数据库路径和身份，不能只看 HTTP 200。用原来的日常方式退出并重新启动，再次确认。源码模式也要确认运行的是拉取后的源码，而不是旧 App 的内置副本。
8. 源码仓库中的旧隐式启动入口应被禁用或改为明确连接新库；使用本地 `.gewu-development-only` 保护标记时，检查日常入口不会因此失效。只保留一个有效日常入口，旧 App 归档为不可误开的备份；不创建两个同时写库的后台。

### 第六步：验收、整理与交付

- 检查一个正式后台、正确数据库身份、原生界面（若原来使用原生 App）、真实 Paper Files 可访问及 PDF 打开、报告和分析、MCP（若已配置）；再次重启后配置持续有效。真实界面操作验证失败必须说明，不能用单元测试替代声明“全部正常”。
- 若为本机启动适配修改了 Python 或 native 代码，运行对应编译和必要的隔离验证；禁止把测试数据写入正式库，不修改无关功能。
- 验收通过后，旧研究目录可归档进已验证的本机备份，使项目只承担开发职责；这是可恢复的整理，不是永久删除。只整理已确认属于旧工作区的内容，保留版本控制所需的 `config` 默认配置以及用户的其他开发文件。暂存、补丁和备份仍保留。
- 在备份目录写一份中文操作记录：原/新源码提交、原/新数据库位置、备份位置、路径适配与本地代码改动、验证结果、原有缺失项、准确的恢复步骤。不记录密钥。新库中出现后续写入后，不得直接回滚丢弃这些写入。
- 恢复时先停止当前服务并保存新数据，再恢复配套的旧软件、旧数据和启动配置；不要让旧软件直接打开已经升级的库，不重置浏览器资料或其他项目。
- 最后只需用中文告诉用户：迁移是否完成、新数据库和备份在哪、以后从哪个入口打开、有什么确实未解决的问题。以后普通源码更新仍由 Codex 退出服务、备份、保护改动、pull 并验证原库；不重复迁移，不要求每次发布 DMG。
